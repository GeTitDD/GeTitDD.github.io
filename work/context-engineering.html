上下文 也是设计

我把上下文看作 Agent 的工作台，也是一项信息架构设计。小模型与个人 Agent 的实践提醒我：堆积历史并不等于补足依据，真正需要设计的是此刻该看见什么、哪些信息仍然有效，以及哪些必须重新核对。

CONTEXT ENGINEERING / 信息架构 · 状态生命周期 · 按需装配

长周期任务往往交织目标、硬性约束、外部资料、历史决策与工具返回。我关心这些信息何时进入、如何分层、何时更新，以及占用多少预算。设计好准入时机、结构层级与生命周期，才能让 Agent 在任务变化时继续使用合适的依据。

我会围绕当前步骤选择材料：检索提供相关来源，工具返回保留关键结果、错误状态与来源入口，关键约束则以清楚、稳定的方式组织。在有限预算下，我会设定材料优先级，保留影响判断的条件和证据。每段进入上下文的内容，都应回答：它能为这一步判断提供什么依据？

信息需要连同状态与来源进入工作。我会区分已确认事实、暂定假设、原始工具证据与过期决策，并注明确认条件和更新时间。外部材料或任务发生变化时，相关结论应重新核对。清楚的分层既减少混用依据的机会，也让开发者能追溯一次判断采用了什么信息。

/ 2

对长任务，我更关注中断后能否接续工作。交接状态至少需要说明：当前目标、已完成事项、仍有效的关键决定，以及未解决的问题。我倾向于把这些内容组织为可继续行动的结构化状态（Actionable State），保留版本与原始证据入口；压缩会话时，也保留影响判断的条件和取舍。

我通过真实任务检查上下文设计：能否找到关键依据，能否识别材料不足，发生冲突时能否回到来源，中断后是否恢复到正确状态。出现偏差时，我会先核对检索结果、记录状态与工具返回，再结合模型能力分析原因，选择重排材料、更新快照或修改返回契约。
