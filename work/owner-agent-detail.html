核心产品与 Agent 架构 / 2026

Owner Pi：多项目统筹与个人领域知识工作台

面向多线并行研发的本地常驻 Agent 控制面与受控执行中枢。双层桌面工作台与 OpenClaw 远程面板协同统筹多项目进度，将运行轨迹与测试证据编译为 L1–L3 不可变知识快照，并在“目录外 Git Worktree → SHA-256 哈希审批 → 零网络 Docker 沙箱验真”的 Fail-Closed 闭环内推进代码演进。

PROJECT CONTEXT / 项目背景

让多项目进度无缝接续，
让每一次踩坑沉淀为资产。

AI 释放了单兵推进多个复杂项目的生产力，却也成倍放大了上下文切换的认知摩擦：进度与决策散落在不同仓库与对话中，而耗费大量精力得出的调试结论，往往随着会话关闭而消散，下一次依然重复踩坑。

Owner Pi 围绕“项目统筹—知识资产—受控执行”三条主线设计：桌面双层工作区接续多项目状态，远程面板提供移动管理入口；运行轨迹与验证证据经人工审核后发布为不可变知识版本；代码变更通过哈希审批与隔离沙箱验证后交由人工裁定交付。

  • 多项目统筹
  • 个人领域知识 (L1–L3)
  • 桌面客户端 & Telegram
  • 受控代码闭环 (Patch-Test-Repair)
01

多项目跟进，认知负担加重

遇到的问题

一个仓库刚完成补丁生成，另一个正在等待沙箱跑测，第三个又有架构方案悬而未决。状态、灵感与待办散落在不同终端与对话流中，每次切换都要耗费大量精力重建心智模型。

对应的产品设计

构建「单项目深度工作区 + 跨项目全局统筹」双层交互模型：上层以 Commit 感知画像接续上下文，下层聚合跨项目决定、异步任务与测试结果；OpenClaw + Telegram 另提供移动项目管理入口。

02

经验随会话流失，难以复用

遇到的问题

环境约束、避坑指南与调试结论隐没在冗长的历史对话里。一旦开启新会话或迁移至新项目，不仅要反复重述背景，大模型也极易重蹈覆辙，过往的排查与验证无法转化为可复用的工程复利。

对应的产品设计

设计 L1 通用原理 / L2 跨项目方法 / L3 单项目约束的三层知识工作台。基于运行轨迹与节点测试证据整理候选经验，经人工审核后发布不可变知识版本；后续会话以 Context Lock 锁定快照，再按项目环境条件检索与装配。

SYSTEM ARCHITECTURE / 系统架构

从确定性知识上下文，
到哈希锁定的受控行动。

桌面工作台汇集项目画像与经过审核的领域知识；Agent 在受限工具面内生成结构化提案。宿主通过双令牌校验请求，人工审批绑定提案哈希，获准变更在隔离 Worktree 内应用，再进入零网络 Docker 沙箱复测，结果回写本地项目状态。

五重人工裁定门禁，逐级显式授权。

批准 Job → 批准补丁（proposal_hash）→ 执行 apply → 批准沙箱 → 失败时批准修复。每个检查点都由人触发，模型无法自行批准或合并。

隔离修改与只读沙箱复测严格串行。

纯问答只读返回，不落 Job。代码提案先在目录外 Worktree 生成；WorkspaceBroker 校验 old_sha / new_sha 并应用隔离工作区补丁后，再创建待审批沙箱复测。

图中标注的对应模块：desktop/main.cjs · owner-store.mjs · workspace-broker.mjs · sandbox-runner.mjs。本页依据所提供的规格与原图整理。

桌面链路的三层边界。

宿主主进程通过 loopback、Host / Origin 与双令牌收敛请求；模型工具面执行二次校验；Docker 使用固定 argv，并在启动后通过 inspect 复核隔离参数。

远程数据面独立存在。

Telegram → Stdio MCP → owner.json，与 SQLite 主链路没有同步。30 个远程工具的清单不能作为本地 Job / Patch / Sandbox 已被远程贯通的证明。

图中标注的对应模块：sidecar-server.mjs · sandbox-provider.mjs · openclaw-owner-mcp/server.mjs。本页依据所提供的规格与原图整理。

四段生命周期，五套状态机。

图中依次展开 Job、Patch、Sandbox 与 Repair；Workspace 是额外一套 CAS 状态机。任务状态之间通过证据与审批衔接，不因模型给出结果而跳过检查。

最多一轮修复，异常交还人。

失败后经批准产生的修复提案回到 Patch.proposed；iteration 1/1，禁止 repair-of-repair。非预期状态统一进入 needs_reconciliation，由人显式裁定。

图中标注的对应模块：owner-store.mjs · patch-protocol.mjs · sandbox-protocol.mjs · repair-service.mjs。本页依据所提供的规格与原图整理。

PRODUCT WORKFLOW / 产品与工作流

将多项目统筹、知识沉淀与受控交付，
收敛于同一工作路径。

桌面工作台承接深度研发，OpenClaw 与 Telegram 补充移动管理——让日常跟进、知识演化与受控交付沿清楚的工作路径推进。

01 / DUAL-LAYER CONTROL PLANE

双层控制面与 17 套只读 Playbook

首页提供「理解项目 / 整理知识 / 复盘沉淀 / 验收 / 修复 / 交付」六个语义动作。选择项目，再说一句要做什么；对话中的改进建议进入想法收件箱，收集后由人决定是否执行。

上层聚焦当前项目：以项目画像与依赖图帮助恢复上下文，并基于 commit 判断画像是否过期；需要深入时进入 17 套 pstack 只读诊断 Playbook。下层集中呈现跨项目决定、异步运行与测试结果，便于找到等待自己处理的事项。

02 / L1–L3 KNOWLEDGE COMPILER

证据驱动知识演化与 Context Lock

将调试结论连同适用环境、测试验证证据与不可变版本一同归档，让后续会话按条件复用，减少反复交底与重新验证的成本。

L1 保存跨项目通用原理，L2 保存跨项目工程模式，L3 保留单项目私有约束。通过 Profile 组合不同领域，并显式判断 applicable / needs_verification / conflict。

运行轨迹与节点测试证据沿 Trace → Evidence → Candidate → Review 演化，经人工审核后原子发布为不可变领域包。会话启动时锁定 Context Lock 快照哈希，让上下文的来源与版本可以复现。

03 / PROPOSAL-EXECUTION SPLIT

提案与执行物理分离

把分析、提案与执行分开，开发者可以检查具体提案，并决定是否进入应用与沙箱验证。交办后的监督有清楚的检查点，减少反复追问与事后排查的负担。

桌面执行链采用事件驱动，默认不持续消耗 Token：先只读分诊与 Playbook 诊断，涉及写操作严格走「目录外 Git Worktree 提案 → 哈希绑定审批 → 零网络只读 Docker 沙箱复测 → 最多 1 轮受控修复」。

04 / HARDENED HOST BOUNDARY

Electron 45 沙箱隔离与 42 通道 IPC 校验

Electron 45 单实例进程托管本地 Runtime；高危决策令牌 approval.token 仅保留在主进程内存。渲染层启用 contextIsolation: true 与 sandbox: true，42 个 IPC 通道逐一校验发送者。

工作台采用零构建原生 ES Modules，并内置防 XSS Markdown 渲染器；交互层专注于呈现与交办，宿主进程管理状态、权限与沙箱边界。

离开电脑时，通过 OpenClaw 与 Telegram 查阅项目画像、记录想法和审核知识候选，为项目跟进与经验整理补充移动入口。远程管理与桌面受控执行保持各自的数据和权限边界。

01 / MCP + TELEGRAM

30 个工具，连接远程项目管理。

Stdio MCP 与 Telegram 面板提供项目切换、画像查阅、想法记录、知识候选审核、图集推送及 Draft PR 等工具入口。面板通过单条消息原地编辑刷新，减少高频操作的消息堆积；规格为高危交互定义了 2 分钟 TTL 二次确认。

交付以 owner/ 分支与 Draft PR 为边界，不自动合并。

02 / FEATURE PLUGIN

5 个工具，收敛模型可见能力。

Feature Plugin 通过 loopback HTTP 连接本地 Sidecar，向模型侧只暴露 5 个受限只读 / 提案工具。在 CI 中断言工具清单，防止审批与落盘能力混入模型工具面。

它与包含 30 个工具的 Stdio MCP 属于不同集成面；数量不相加成同一套执行权限。

当前实现边界 / 以数据流原图为准

Telegram / Stdio MCP 读取独立的 ~/.owner-companion/owner.json，目前与桌面 SQLite 没有同步逻辑；MCP 仅启动插件 worker，不访问 Sidecar。远程面板看到的也不是本地 Job / Patch / Sandbox 状态。

图中 Telegram 以 chatId 校验入口，MCP Server 未设认证；桌面链路的双令牌鉴权不能直接归给远程数据面。本页将其展示为独立远程管理入口，不将工具清单等同于远程安全执行闭环已贯通。

ENGINEERING DESIGN / 工程深潜

模型提出行动，
系统管理执行边界。

ENGINEERING NOTE / 01

跨项目知识资产化与
确定性上下文编译

要解决的问题

多项目经验难以沉淀；直接把全量文档塞进 Prompt，又会超出上下文预算并稀释有效信息。

工程解法

设计 L1 / L2 / L3 分层知识模型，沿 Trace → Evidence → Candidate → Review 演化。已发布版本不可变，会话以 sharedSnapshotId + projectSnapshotId 锁定双快照并导出 Context Lock。运行时通过 FTS5 + BM25 启发式重排与硬 Token 预算装配上下文。

知识需要能追溯到版本、适用条件与证据，而不只是能被检索到。

ENGINEERING NOTE / 02

无状态会话执行器，
在工具边界处停止越权

要解决的问题

长对话积累噪声，全局扩展插件还可能让只读分析意外获得写文件权限。

工程解法

以 SessionManager.inMemory() 包装一次性内存会话，每次调用创建干净的隔离目录。只读分诊、pstack 诊断、代码写入分别采用工具白名单；创建后再用 getActiveToolNames() 枚举断言，工具面不匹配就 Fail-Closed 终止。

模型能调用哪些工具，由宿主显式限定，并在真正执行前再次核对。

ENGINEERING NOTE / 03

哈希绑定提案，
复核真正生效的沙箱

要解决的问题

避免模型直接改主工作区，防止审批后补丁被替换，同时核对容器隔离是否实际生效。

工程解法

写操作在项目目录外的 Git Worktree 中生成，每次提案、沙箱与修复绑定 SHA-256。审批后先校验并应用隔离工作区补丁，再在人工批准的 Docker 沙箱中复测：--network none --read-only --cap-drop ALL，配合只读挂载。启动后立即通过 docker inspect 复核实际参数；Docker 不可用即失败，不降级到宿主机执行。

批准绑定具体内容；隔离条件也必须有运行时证据。

ENGINEERING NOTE / 04

有界单轮修复，
守住崩溃后的状态一致性

要解决的问题

休眠、断电与进程强杀会留下中间状态；自动修复循环也可能破坏测试断言或陷入无限重试。

工程解法

5 套 CAS 状态机配合租约、心跳与 Attempt 栅栏防止脏写。测试失败后最多允许 1 轮受控修复（iteration 1/1），排除 tests/ 修改并校验测试文件哈希。异常进入 needs_reconciliation，保留并隔离现场，由人决定后续动作，不盲目回滚。

修复有次数上限，恢复有人工裁定，不能把不确定状态当作成功继续推进。
